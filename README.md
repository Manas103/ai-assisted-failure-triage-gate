# AI-Assisted Failure Triage with a Deterministic Reproduction Gate

A triage pipeline for CI and production failure records: cluster 4,000
synthetic failures into signatures, attribute a root cause to every
record with a deterministic classifier, then file that root cause only
after two independent, real gates both go green: a generated
reproduction that fails on the suspect build and passes on the fix, and
a proposed regression test that kills the mutant standing in for its
defect. Python, pytest, DuckDB, a hand-rolled mutation harness (mutmut
installs but will not run natively on Windows, see Findings). Every
number below was measured on this machine on 2026-09-11, not targeted;
where a first measurement was wrong, the wrong number and the fix are
both kept in Findings rather than silently replaced.

## Why this exists

A triage assistant that can name a plausible root cause for a failure is
only useful if there is a real bar for filing that root cause. This repo
is a small version of that bar: nothing is "filed" (accepted as a real
attribution) unless it survives an actual subprocess run of a generated
reproduction against the buggy code and the fix, and an actual mutation
kill of a proposed test against a hand-mutated copy of the fix. Both
checks are real code execution, not string comparison against a
precomputed answer.

## Honest framing

- **12 of the 40 ground-truth signatures are backed by a real, small,
  genuinely buggy Python module and its real fix** under
  `fixtures/sig01.../{buggy,fixed}.py` through `fixtures/sig12.../`. The
  other **28 of 40 are textual-pattern-only**: a plausible CI/production
  failure shape (error type, message template, synthetic file/function)
  with no backing implementation, used to exercise clustering and
  attribution at the full 4,000-record scale. This mirrors the
  real-vs-scripted disclosure pattern in this portfolio's
  [ai-assisted-legacy-batch-migration-gate](https://github.com/Manas103/ai-assisted-legacy-batch-migration-gate)
  (8 of an intended 40 drafts real) rather than padding the real count.
- **All 4,000 records are synthetic**, generated by
  `src/triage/generate_records.py` with a fixed seed (20260911); real
  per-record noise (jittered line numbers, a random hex frame address, a
  random identifier-with-digits token, a random count) is injected on
  top of each signature's fixed template.
- **The 12 real bugs are original to this repo**: a pagination
  fencepost, a timezone-naive/aware comparison, an inclusive/exclusive
  range boundary, a stale TTL cache, a float-equality-instead-of-
  tolerance bug, a mutable default argument, integer division
  truncation, a byte-vs-character truncation bug, a missing sort
  tie-break key, a dedupe key collision, a retry-loop off-by-one, and an
  overly broad `except` clause. None overlap the race-condition bug in
  [ops-console-regression-gate](https://github.com/Manas103/ops-console-regression-gate)
  or the rounding-mode/weekend-rollover bugs in
  ai-assisted-legacy-batch-migration-gate.
- **`mutmut` 3.7.0 installs cleanly in this project's venv** (`pip show
  mutmut` succeeds) but its own CLI refuses to run on native Windows
  ("To run mutmut on Windows, please use the WSL", verified 2026-09-11,
  `docs/mutmut_attempt.txt`). The mutation-kill gate is hand-rolled
  instead: each real fixture's `fixed.py` declares 2 hand-chosen mutants
  (a flipped comparator, a shifted boundary, a dropped check, a swapped
  branch), applied as a real text patch to a real temporary file and
  executed, per BUILDER's precedent for hand-rolled check suites when the
  standard tool does not fit.
- **The `claude -p` cross-check is a genuine, disclosed, small live
  sample**: 15 of the 4,000 records, not the mechanism the 92%-class
  accuracy claim is measured against (that is the full 4,000-record
  deterministic run). Raw transcript: `docs/claude_crosscheck_raw.txt`.
- Machine and toolchain: 8 physical / 16 logical cores, Windows 11 Home
  (build 10.0.26200), Python 3.12.10 (Windows-native venv), DuckDB
  1.5.5, pytest 9.1.1, mutmut 3.7.0 (installed, not runnable natively,
  see above).

## Architecture

```
src/triage/
  signatures.py       the 40 ground-truth signatures: 12 real-fixture, 28 textual-only
  generate_records.py builds 4,000 synthetic records (seed 20260911) into DuckDB
  cluster.py           deterministic template-hash normalizer + clusterer + recovery scoring
  attribute.py          deterministic per-record signature classifier (exact + nearest-neighbor fallback)
  repro_gate.py         Gate 1: generates and subprocess-runs a reproduction vs suspect/fix
  mutation_gate.py      Gate 2: hand-rolled mutants of fixed.py + subprocess kill check
  llm_crosscheck.py     genuine claude -p spot-check on a 15-record live sample
  measure.py             runs clustering + attribution over the full batch, writes docs/ reports
  triage_cli.py          the one script: cluster, attribute, gate, file/reject, print + write report
fixtures/sig01.../sig12.../
  buggy.py, fixed.py     real defect + real fix pair, REPRO_CASES, MUTANTS (see each docstring)
tests/
  test_signatures.py, test_generate_and_cluster.py, test_attribute.py, test_gates.py
  regression/test_fixtures_direct.py   in-process pytest coverage of every real fixture
docs/
  clustering_results.txt, attribution_report.txt, measure_summary.json
  gate_decisions.txt, gate_decisions.json
  claude_crosscheck_raw.txt, claude_crosscheck_report.txt
  mutmut_attempt.txt, test_output.txt
```

**Why normalization strips digit runs without a word-boundary
requirement.** The first version used `\b\d+\b`, which does not match a
digit run immediately followed by a unit letter (`"710s"`, `"12ms"`).
Every signature whose message template ends a number in a unit suffix
fragmented into one cluster per distinct random value instead of one
cluster per signature. See Findings for the measured before/after.

**Why attribution is a separate mechanism from clustering, not a
relabeling of its clusters.** A real triage system has a signature
library curated once, offline; `attribute.py` builds exactly that (one
canonical, noise-free rendering per signature, normalized the same way
as real records) and matches new records against it independently of
however records happen to batch together in a given run.

**Why the repro and mutation gates generate and run a real subprocess
script instead of comparing Python objects in-process.** A "generated
reproduction" that never leaves the parent process could accidentally
share state (imported modules, monkeypatches) between the suspect and
fix checks. Each check writes a fresh `.py` file to a temp directory and
runs it with `subprocess.run([sys.executable, ...])`, so the suspect and
fix runs are fully isolated processes, and the generated script itself
is inspectable in the gate's returned report.

## Findings

**A real normalization bug, found and fixed, changed the recovered count
from 30/40 to 40/40.** The first clustering run over the full 4,000
records produced 797 distinct clusters and recovered only 30 of the 40
true signatures. The discriminating fact: several signature templates
end a random number in a unit suffix with no space (`"returned a value
710s past ttl expiry"`, `"waited 12ms"`), and `\b\d+\b` requires a word
boundary on both sides of the digit run, which does not exist between a
digit and a following letter. Every record's exact random value survived
normalization, so records of the same true signature hashed to different
clusters. Root cause: the boundary-anchored regex, not the clustering
method. Fix: drop the boundary requirement (`\d+` unanchored); rerun
gave 40 clusters and 40/40 signatures recovered. Both the 30/40 and the
40/40 numbers are real measurements of the same code before and after
the fix, not a discarded draft.

**The mutation gate correctly refused 2 of the 12 real fixtures, and the
reason is a genuine equivalent-mutant case, not a broken gate.**
`sig02_tz_naive_compare`'s "drop the expiry tzinfo normalization" mutant
and `sig11_retry_backoff_offbyone`'s "remove the attempt increment"
mutant both survive their fixture's proposed test: for sig02, the
`REPRO_CASES` never call `is_expired` with a naive `expiry` argument, so
removing expiry's own normalization branch does not change behavior on
this test's inputs; for sig11, the retry loop's condition stays true
forever once incrementing is removed, so a flaky function that succeeds
within a few calls still eventually returns the right answer through the
same call, just via an unbounded loop instead of a bounded one. Both are
real, disclosed mutation-testing limitations (an equivalent-mutant-on-
this-test case), not a defect in the gate itself: the gate's job is to
refuse admission when it cannot prove the test discriminates the defect,
and it does refuse both.

**0 unproven attributions filed, by construction.** `triage_cli.py`
only marks a signature's attribution `filed` when both
`repro_gate.check_root_cause(...).accepted` and
`mutation_gate.check_test_admission(...).admitted` are `True` in the
same run; the two rejected signatures above are counted as `rejected`,
never `filed`. 12 real-fixture proposals ran through both gates this
session; 10 filed, 2 rejected, 0 filed without both checks green.

## Limitations

- Clustering and attribution both reach a clean 100%/40-of-40 on this
  synthetic corpus once the normalization bug was fixed; that is a
  property of a deterministic template-hash approach on data generated
  from the same 40 fixed templates it is scored against, not evidence
  the method would separate a noisier, real-world log corpus this
  cleanly. A real corpus would need a softer similarity measure.
- 12 of 40 signatures have real fixture code; the other 28 are textual
  patterns only, stated up front rather than left implicit.
- 2 of 12 real fixtures' proposed tests do not kill all their hand-rolled
  mutants (an equivalent-mutant case on this specific test, see
  Findings); the gate correctly refuses both rather than filing them.
- `mutmut` is installed but not exercised as the mutation engine because
  it does not run natively on Windows; the mutation gate is hand-rolled
  per fixture instead (2 mutants per fixture, 24 total).
- The `claude -p` cross-check covers 15 of 4,000 records, a disclosed
  spot-check, not the accuracy measurement itself.
